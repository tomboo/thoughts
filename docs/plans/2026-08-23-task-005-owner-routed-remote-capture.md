# Task 005 Owner-Routed Remote Capture Plan

## Goal

Let the MacBook and iPhone create thoughts that land in the iMac's canonical
`.thoughts/thoughts.sqlite`, without either device holding a writable canonical
database of its own.

Create-only. Remote edit, delete, sync, and search stay out of scope.

## Non-Goals

- No remote edit, delete, status change, sync, or search.
- No long-running network daemon and no listening port owned by this project.
- No direct SQLite access over the network.
- No local fallback that silently creates a second canonical database when the
  owner is unreachable.
- Tailscale is connectivity only, never the authorization boundary.

## Shape Of The Solution

Three pieces, each small:

1. **A wire protocol** — one JSON capture request in, one JSON response out.
2. **An owner-side receiver** — `thoughts receive`, which reads one request on
   stdin and performs exactly one create against canonical SQLite.
3. **A client-side submitter** — `thoughts remote capture`, which builds a
   request, pipes it to the owner over SSH, and spools to local disk when the
   owner is unreachable.

The transport is `ssh`. The receiver is a short-lived process the owner's SSH
session starts, so there is nothing listening and nothing to authenticate
beyond the SSH key the operator already manages. Tailscale supplies the route
when the client is off-LAN; it changes the address, not the trust model.

### Why stdin/stdout over HTTP

An HTTP receiver would mean a daemon, a port, a bind address, and a second
credential system, all to move one JSON object. `ssh owner thoughts receive`
reuses an existing authenticated channel and keeps the write surface to a
single create-only verb. The project also has exactly one runtime dependency
(`pyyaml`); a web framework would be the largest thing in it.

## Protocol

Request — one JSON object on stdin:

```json
{
  "protocol_version": 1,
  "request_id": "req_0f3a...",
  "submitted_at": "2026-08-23T21:04:11.221Z",
  "origin": "macbook",
  "thought": {
    "body": "Body text",
    "title": "Optional title",
    "type": "inbox",
    "tags": ["capture"],
    "due": null,
    "priority": null
  }
}
```

Response — one JSON object on stdout:

```json
{
  "protocol_version": 1,
  "status": "created",
  "request_id": "req_0f3a...",
  "thought_id": "th_85c7...",
  "received_at": "2026-08-23T21:04:11.402Z"
}
```

`status` is one of `created`, `duplicate`, or `rejected`. A `rejected` response
carries `error` instead of `thought_id` and exits non-zero.

Rules:

- `request_id` is generated by the client and is the idempotency key.
- `origin` is a short device label matching `^[a-z0-9][a-z0-9-]{0,31}$`.
- The owner sets `source` to `remote:<origin>`. Clients cannot choose their own
  `source`, so a remote write can never claim to be a local `cli` write.
- Unknown top-level or thought keys are rejected rather than ignored, so a
  newer client fails loudly against an older owner.
- `protocol_version` must equal 1.

## Duplicate, Offline, And Retry Behavior

This is the part that has to be right, because the failure mode that matters is
a request that succeeds on the owner and then dies on the way back.

**Duplicates.** Migration 3 adds `capture_requests`, keyed by `request_id` and
referencing the created thought. `receive` looks the key up first: a known key
returns the original `thought_id` with `status: "duplicate"` and writes nothing.
The insert of the thought, its tags, and the `capture_requests` row happen in
one transaction, so a crash mid-write leaves no half-recorded request.

**Retries.** The client reuses the same `request_id` for every attempt at the
same thought. Retrying after a timeout is therefore always safe: either the
first attempt never landed and this one creates the thought, or it did land and
this one reports `duplicate` with the same id.

**Offline.** If the transport fails, the client writes the request JSON to a
spool directory (`~/.local/state/thoughts/spool`, overridable) and reports
`spooled` with the request id. It does not create a local database — a
non-owner machine that cannot reach the owner accumulates queued requests, it
does not become a second writer. `thoughts remote flush` drains the spool
oldest-first, deleting each file only after the owner confirms `created` or
`duplicate`. A `rejected` request moves to a `rejected/` subdirectory instead of
being retried forever.

## Implementation Steps

### 1. Migration 3 — `capture_requests`

```sql
CREATE TABLE capture_requests (
    request_id TEXT PRIMARY KEY,
    thought_id TEXT NOT NULL REFERENCES thoughts(id) ON DELETE CASCADE,
    origin TEXT NOT NULL,
    submitted_at TEXT,
    received_at TEXT NOT NULL
);

CREATE INDEX idx_capture_requests_thought ON capture_requests(thought_id);
```

`open_store` does not migrate, so both machines run `thoughts init` once to pick
this up. `init` is idempotent.

### 2. `src/thoughts/remote.py` — protocol and owner-side receive

- `CaptureRequest` / `CaptureResponse` frozen dataclasses.
- `parse_request(text)` — strict JSON decode and validation, raising
  `ProtocolError` for anything malformed.
- `receive_capture(conn, request)` — idempotent create, returns a response.
- `new_request_id()` alongside the existing `ids.new_thought_id()` style.

### 3. `src/thoughts/submit.py` — client-side submit and spool

- `RemoteConfig` — owner command (argv list) and origin label, resolved from
  `THOUGHTS_OWNER_COMMAND` / `THOUGHTS_ORIGIN` env vars, else
  `~/.config/thoughts/remote.json`.
- `submit(request, config)` — run the owner command, pipe JSON to stdin, parse
  the response, raise `TransportError` on failure.
- `spool_request` / `iter_spooled` / `flush_spool`.

### 4. CLI surface

Owner:

- `thoughts receive [--export]` — read one request on stdin, create, print the
  JSON response. `--export` refreshes Markdown projections afterward so a
  one-shot iPhone capture produces a committable file.

Client:

- `thoughts remote capture <text> [--title --type --tag --due --priority]`
- `thoughts remote flush`
- `thoughts remote status`

The client commands never call `open_store`, which is what structurally
guarantees they cannot write a local canonical database.

### 5. Status surface

Add `remote_capture_requests` to `StatusSummary` and the `status` output so the
owner can see how many thoughts arrived remotely.

### 6. Tests — `tests/test_remote.py`

- Valid request creates exactly one thought with `source = remote:<origin>`.
- Replaying the same `request_id` returns `duplicate` and leaves the count at 1.
- Malformed, unknown-key, wrong-version, and invalid-`origin` requests are
  rejected without writing.
- A rejected request rolls back cleanly — no orphan `capture_requests` row.
- `remote capture` against a stub owner command creates the thought owner-side.
- Transport failure spools; `remote flush` against a working stub drains it and
  the thought lands once.
- Flush over an already-received request id ends at one thought, not two.

### 7. Docs

- ADR 0002 recording the owner-routed create-only decision and the SSH choice.
- `docs/ops/remote-capture.md` — the operator runbook: MacBook setup, the iPhone
  Shortcuts route, offline/retry semantics, troubleshooting.
- Update task `005`, and note in task `003` which of its criteria this covers.

## Verification

1. `uv run pytest`, `uv run ruff check`, `uv run mypy` on the MacBook.
2. `thoughts init` on the iMac to apply migration 3.
3. From the MacBook: `thoughts remote capture "..."` and confirm the id appears
   in the iMac's `thoughts status`.
4. Retry the same request id and confirm the count does not move.
5. Break the owner command, capture, confirm `spooled`, restore, `remote flush`,
   confirm exactly one new thought.

## Risks

- **The iMac cannot push to GitHub yet** (recorded in the owner handoff note).
  Remote capture lands in owner SQLite regardless, but projections will not
  reach the MacBook until that is fixed.
- **SSH key sprawl.** The capture path is only as narrow as the SSH
  authorization behind it; a full shell key can do far more than capture.
  Constraining it to a forced command is the natural follow-up, deferred here
  and noted in the ADR.
